# WRITING DOCUMENTS

> What the builder does with a file, so you can write one that comes out the way you meant.
> Nothing here is a special syntax to learn — it is ordinary Markdown, read with a few
> conventions about what the first lines of a document mean.

---

## 1. What the top of a file becomes

The first three things in a file have jobs:

```markdown
# TITLE OF THE DOCUMENT          ← the page heading, and the sidebar entry

> One or two sentences saying    ← the standfirst under the heading
> what this document covers.

---                              ← optional, ignored

## 1. The first real section
```

The `# H1` is lifted out and used as the title, so it never appears twice. The blockquote directly
under it is lifted out the same way and shown as the standfirst. Everything after that is the body.

A file with no `# H1` keeps its filename as the title. A file with no blockquote simply has no
standfirst.

## 2. How documents are ordered and grouped

A leading number in the filename decides the order, and a plain sort will not do — `10.` has to
follow `9.`, not `1.`. So the number is read as a number.

| Filename | Sorts as | Sidebar badge |
|---|---|---|
| `0. ABOUT.md` | 0 | `0` |
| `2. DIAGRAMS.md` | 2 | `2` |
| `10. TESTING.md` | 10 | `10` |
| `GLOSSARY.md` | after all numbered files, alphabetically | `G` |

Sub-folders become their own sidebar group, named after the folder. Anything second-class —
audits, reviews, meeting notes, one-off reports — belongs in one, so the main run stays the main
run:

```
docs/
  0. ABOUT.md          ─┐
  1. WRITING.md         ├─ group "Documents"
  2. DIAGRAMS.md       ─┘
  audits/
    2026-09-04.md      ─── group "Audits"
  schema/
    tables.dbml        ─── group "Schema"
```

Fix the order of the groups with `groupOrder` in [the config](./3.%20CONFIGURATION.md#groups);
anything not listed follows alphabetically.

## 3. Sections

Every heading owns everything under it until the next heading of the same or higher level. That is
what lets a section [fold away](./4.%20READING.md#folding) as a unit, and it is why the spacing
between two sections is one rule rather than a stack of heading margins.

Sections are numbered from their nesting, not from their level — a document whose top level is `##`
still starts at 1. **A heading that numbers itself keeps its own number:** if you write
`## 3. Claiming a profile`, it stays 3, because the prose around it says "the diagram in 3.2" and
an invented second number would contradict that.

A `---` written directly above a heading is dropped. The section rule draws that line itself, and
two lines in the same place look like a mistake.

## 4. Links

Links between documents are rewritten into in-page navigation, so following one does not reload
anything and the back button still works.

| You write | What happens |
|---|---|
| `[Diagrams](./2.%20DIAGRAMS.md)` | opens that document in the dashboard |
| `[a section](./2.%20DIAGRAMS.md#why-elk)` | opens it at that heading |
| `[below](#three-ideas)` | scrolls, and unfolds anything folded on the way |
| `[the repo](https://example.com)` | opens in a new tab, untouched |

Heading anchors are the GitHub ones — lowercase, spaces to hyphens, punctuation dropped — so a link
written for GitHub keeps working here, and a link written here keeps working on GitHub. That is the
point: the folder must stay readable in both places.

Use `%20` for spaces in filenames, as GitHub does.

## 5. What is rendered

| Construct | Notes |
|---|---|
| Headings, paragraphs, lists, nested lists | as expected |
| **Bold**, *italic*, `code`, ~~strikethrough~~ | `_snake_case_` is left alone, not turned into emphasis |
| Tables | alignment row respected; a `\|` inside a code span does not split a cell |
| Fenced code | the language is shown as a tag in the corner |
| ```` ```mermaid ```` | becomes a diagram — see [Diagrams](./2.%20DIAGRAMS.md) |
| ```` ```api ```` | becomes an API call box — see [API calls](#api-calls) below |
| ```` ```http ```` | drawn as the example it is: verb (or a response's status) and url on top, then the headers, then the body — see [API calls](#api-calls) |
| ```` ```json ```` | coloured: keys, strings, numbers and `true`/`false`/`null` each have their own colour |
| ```` ```sql ```` | coloured: keywords, types, functions, strings, numbers, `@variables` and comments — also as `tsql`, `postgres`, `mysql` |
| `` `POST` ``, `` `GET /users/{id}` `` | a code span holding an HTTP verb, alone or before a url, takes the verb's colour |
| Blockquotes | including multi-paragraph ones |
| Images | `![alt](path)`, lazily loaded |
| `<br/>`, `<a id="x"></a>` | the two bits of raw HTML documents genuinely need |
| `<!-- comments -->` | stripped — a commented-out section renders as nothing |

Anything else is left as literal text rather than guessed at. If you need a construct that is not
in this table, it probably belongs in prose instead.

### API calls

An ```` ```api ```` block draws one call as a box, its verb in the verb's colour. The first line is the
request; after it, one `part: description` line for each part of the url worth explaining — a
`{placeholder}`, or a fixed piece of the path. Lines indented under a part continue its
description, and a `- ` line among them becomes a bullet: a good place to say what the value may
and may not be.

````
```api
PUT https://{host}/api/v1/submissions/{submissionId}/batches/{batchNumber}

{host}: domain exposed by the gateway
{submissionId}: the submission opened earlier
{batchNumber}: number of the batch, chosen by the caller
  - starts at 1
  - no gaps
```
````

The box shows only its header — the verb and the url — until it is clicked; the body then lists
every described part. Folded, it still answers: hold **Ctrl** (**Option** on a Mac) with the
pointer on a part of the url and its description appears, without opening anything.

A block with no descriptions is just the header, and does not open.

An example of a call is an ```` ```http ```` block: the request line, the headers, a blank line,
the body. It is drawn with the same header as an ```` ```api ```` box, the headers listed under it
and a JSON body coloured. A status line — `HTTP/1.1 409 Conflict` — starts a response, and its
badge takes the colour of the status: green for 2xx, blue for 3xx, orange for 4xx, red for 5xx.
Written after the request, following a blank line, the response goes in the same box, under it;
a block can also hold a response alone.

````
```http
POST https://{host}/api/v1/submissions
Content-Type: application/json

{ "companyCode": "EM14", "period": { "year": 2026, "month": 4 } }

HTTP/1.1 201 Created
Location: /api/v1/submissions/1042

{ "submissionId": 1042, "status": "OPEN" }
```
````

## 6. Files that are not Markdown

A schema dump, a data file, a query — anything listed under `verbatim` in
[the config](./3.%20CONFIGURATION.md#file-types) is shown verbatim in a code block, with its own
sidebar group. This keeps the artefact next to the document that explains it, without pretending
it is prose.

## 7. Conventions worth adopting

None of these are enforced. They are what makes a set of documents read as one set.

- **One topic, one owning file.** A restatement in a second file is a future contradiction. Link
  instead.
- **Describe the experience, not the mechanism** — in product documentation, at least. What a
  person sees and gets back, not which function runs.
- **Every "see the other doc" is a link.** If it is worth referring to, it is worth clicking.
- **Open questions live at the bottom**, in their own section, marked as questions. Anything
  settled belongs in the body.
- **Wrap prose at about 100 columns.** It diffs better and the rendered page does not care.
